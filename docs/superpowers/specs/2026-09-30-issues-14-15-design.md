## Part A — issue #14: the read-back confirms the note it shows

### What happens today

`note_confirmed` rule (3) (server/sweep.py) requires the confirming read's
`note_seen_at` (the `imported_at` of the read's snapshot) to be at least
`CEILING_ASSUMED_S` after `note_issued_at`, the last time an `add_note` was handed out
for the lineage. A read-back in the pass that issued the note always fails it
(`imported_at` precedes the issue), so the next import finds the note unconfirmed, the
row is due again, and a later pass reads it once more and writes nothing. A first
catch-up costs about 2N reads.

### Why rule (3) exists, stated as the property it protects

A confirmation says: *the row's newest accounting note is the lineage's current note, and
stays so*. It can be falsified after the read only by a plugin `add_note` that lands after
the read with a **different** body — an older revision carried out late (round D1), or a
held read recorded after such a write (round D2). An `add_note` of the **current** body
landing later leaves the same text on top, so it cannot falsify it. Note texts carry the
store-wide `note_seq` ("Accounting revision N: …"), so within one store generation two
different bodies never share a text.

Every write the plugin hands out is carried out within `CEILING_ASSUMED_S` of being
issued or never (spec assumption A2). A read belongs to a snapshot whose `imported_at`
precedes the read (the specialist lists the row after the import). So:

> A read that shows the current note last is final iff every `add_note` of any **other**
> body was issued at least `CEILING_ASSUMED_S` before the read's `imported_at`, and so
> was every write a previous store generation could have issued.

Today's rule is this rule with "other body" widened to "any body"; that widening is the
whole cost of #14.

### The change

New columns on `projections`:

- `note_issued_seq` — the `note_seq` of the last `add_note` handed out (set with
  `note_issued_at`).
- `note_other_issued_at` — the latest issue time of an `add_note` whose `note_seq` differs
  from `note_issued_seq`.

Maintained in `record_observation` where `note_issued_at` is stamped today: if
`note_issued_seq` differs from the `note_seq` being issued (or is NULL while
`note_issued_at` is set), then `note_other_issued_at := max(note_other_issued_at,
note_issued_at)` (the previous issue becomes an "other"; the max keeps a later issue a
merge brought in — D1, Astra S2; NULL-safe: SQLite's `max(NULL, x)` is NULL, so a NULL
`note_other_issued_at` counts as no issue — D2, Terra S1); then
`note_issued_at := now`, `note_issued_seq := note_seq`. By induction
`note_other_issued_at` is the latest issue of any seq other than `note_issued_seq`.

New meta key `store_epoch_at`: set when the store is created (fresh DDL), by
`reset_store`, and by the 5 → 6 migration (conservative: the time of the upgrade). It
stands for every write an earlier store generation (or an earlier plugin version whose
issues were not recorded by seq) could have issued.

`note_confirmed` rule (3) becomes:

    other := note_other_issued_at                      if note_issued_seq = note_seq
             max(note_issued_at, note_other_issued_at) otherwise (NULLs ignored)
    bound := max(other, store_epoch_at)
    confirmed (3) iff note_seen_at > bound + CEILING_ASSUMED_S   (strict — D1, Terra S1:
                  stamps are whole seconds and A2 allows a write AT the ceiling)

Rules (1) (the note seen is the current one) and (2) (the tag revision is the one the read
saw) are unchanged. The old rule is the special case where the current body was never
issued; it is never weaker than today's where it matters: `bound` includes every
different-body issue that today's `note_issued_at` covered.

Merge (`ledger.merge`): the loser's issued writes target the same row now, and none of
them carries the survivor's current seq (seqs are store-unique), so the survivor's
`note_other_issued_at := max(its own, loser.note_issued_at, loser.note_other_issued_at)`.
(Today a merge carries none of the loser's issue times — a gap this closes.)

Migration 5 → 6: `note_issued_seq` NULL everywhere, `note_other_issued_at := note_issued_at`
(an issue whose seq is unknown is treated as "other"), `store_epoch_at := now`.

### Cost and residuals

- In the measured catch-up (121 of 143 lineages had one `add_note`), the read-back
  confirms and the second read disappears. A lineage re-noted with a new revision still
  waits one ceiling after the earlier revision's issue, and then confirms at its next read.
- Nothing is confirmed by a read in the first `CEILING_ASSUMED_S` after install, reset or
  upgrade (as today).
- The residuals of issue #1 §3 (a confirmed note dropping out of sight without a tag
  change; casa-specialist-finance#89) are unchanged.
- Rule (3) still rests on A2 (a delegation ends at its ceiling) and on the read following
  its snapshot's import — the same assumptions as today, no new ones.

## Part B — issue #15: a package request runs the quarter's check

### What happens today (0.3.5)

`begin_pass(trigger="package")` → `record_step(step="snapshot", quarter, channel)` opens
the request → the specialist syncs, imports and sweeps the quarter → `end_pass` hands a
`package_token` to build. No Gmail round, no judging: an invoice emailed since the last
weekly check ships as "still missing". A package asked for while a pass runs is answered
`busy`. "Send me the last package you built for Q3" is not understood.

### Operator rulings (2026-09-30, on the issue)

1. A package request's Gmail round and judging cover only the requested quarter's open
   items.
2. The package is never shipped partial on a time limit: the check continues across
   continuations until it is done, then the zip arrives.

### The model: a request, worked in rounds

A **package request** is now opened when the package is asked for, and lives until its
package is built (or it is closed). Its **check** is worked in **rounds**; each round is
one package pass, as today's, with the steps a check has:

    snapshot (specialist: probes, sync, import, ends, the quarter's sweep)
    → Gmail round (Ellen: the quarter's work list)
    → judge (specialist: the quarter's triage, then the sweep once more)
    → end_pass → the request's fate for this round

`FOR_TRIGGER["package"] = ("snapshot", "judge")`.

**Request states.** New state `queued`: asked for (or between rounds), no pass working on
it. `snapshot` keeps its meaning (a round runs in `pass_id`). `pass_id` becomes nullable
(a queued request that never had a round has none). New columns: `round` (rounds
finished), `remaining` (the last round's remaining count, below), `check_json` (what the
caption must say about the check: `{"gmail": "down"}`, `{"unfinished": n}`).
Schema 6 rebuilds `package_requests` (SQLite cannot alter a CHECK). Rows carry over,
except that a request an older version left buildable without a check — `snapshot-done`
or `built` (built, not yet staged) — goes back to `queued` with its token, lease and
`package_id` cleared, so the new flow checks it before anything is built or sent (D1,
Astra S1). A request in `snapshot` keeps its pass; its round ends through `round_fate`
like any other. Staged and closed requests are unchanged.

**What the check needs, per round** — computed server-side at the round's end, in
`end_pass`'s transaction (and in the reclaim's), for the request's quarter Q:

- `unsearched`: Q's work items — triage items (`work._needs_search`) of Q that are fresh
  and not `portal` — whose last *search effort* (`record_search` with queries, a
  candidate, or `exhausted`; the existing `last_searched_at`) is older than the request's
  `created_at`. **Ordered by the store sequence, not by time** (D1, Terra S1: stamps are
  whole seconds, so a search in the request's own second compared equal): the request
  stores `created_seq := db.next_seq` when it is opened, `record_search` stores
  `searched_seq := db.next_seq` with every search effort, and an item counts as searched
  for the request iff `searched_seq > created_seq` AND the search's recorded facts
  fingerprint (`R.facts_of` of the live row, stored with the search) equals the payment's
  current one (D3, Terra S1: a payment whose amount or date changed since it was searched
  is searched again). Zero when this round's Gmail probe (`record_probe(kind="gmail")` in this
  pass) failed.
- `unjudged`: Q's judge-due payments (`work.judge_due_state` restricted to Q) not covered
  by this round's judge step. Covered needs more than `_judgment_owed`'s rule (D1, Astra
  S1: a judge step that finished out of time was credited with payments it never
  reached): the judge step finished, not `failed`, not `stopped`, not `out_of_time`, with
  `triage_remaining = 0` — the specialist went through every page — and the payment was
  due in the same state when it started. Otherwise every judge-due payment of Q counts.
  `steps.finish` now stores `out_of_time` in `finish_json` (D3, Astra S2: it was dropped,
  so a timed-out finish looked complete).
- `incomplete` (D3, Astra S1: an empty quarter, or a reclaimed round, had nothing left to
  count and so looked done without any Gmail round): 1 unless this pass recorded a Gmail
  probe (Ellen's Gmail round began) AND its judge step finished as above (Ellen starts it
  only after her Gmail round, self-mail search included). 0 otherwise.
- `remaining := unsearched + unjudged + incomplete`.

The quarter's sweep is not part of it: it puts tags and notes on bank-feed; the zip
reads classifications from the import and pairings from the store. (Today's package
already ships whatever the sweep did not reach.)

**The round's fate** (`round_fate`, the ONE place a request leaves `snapshot`; today's
`snapshot_fate` becomes its first half):

1. Stopped (the stored snapshot finish or the outcome says so) → closed `stopped`, as today.
2. This pass did not import, or the outcome is `failed` → closed `recovery-failed`, as today.
3. `remaining = 0` → buildable (`snapshot-done`); `check_json` records `{"gmail":"down"}`
   when the Gmail probe failed.
4. `remaining > 0` and (this is the first round, or `remaining` < the previous round's)
   → back to `queued`, `round += 1`, `remaining` stored. The next round starts as soon as
   no pass is live (below).
5. `remaining > 0` and no progress (`remaining` ≥ the previous round's) → buildable, with
   `check_json = {"unfinished": remaining}`: the check cannot get further, so the package
   ships and says so. This is not a time limit: a round that searched or judged anything
   the previous one had not reached counts as progress. There is no round cap (D1, Astra
   S1: a cap ships an ordinary backlog unfinished while every round makes progress). The
   loop ends because `remaining` is a non-negative integer that must fall every round;
   it can rise only by new work arriving from outside (new payments in Q, a pairing the
   operator rejects), and a round that fails to beat its predecessor ships.

**Rounds follow each other without the operator.** A round ends in `end_pass` (Ellen's,
as today, or a reclaim's). When a queued request exists and no pass is live:

- `end_pass` answers `next: "continue"` (with the ended pass's own fields as today);
  Ellen calls `continue_pass()` straight away.
- `continue_pass` (`steps._choose`) takes the oldest queued request when no pass is live:
  in its claiming transaction it starts a package pass for it (the same marker/token code
  as `begin_pass`, `reply="silent"`), sets the request to `snapshot` with that `pass_id`,
  and answers `{"continue": {pass_token, pass_id, trigger: "package", step: null, next:
  "snapshot", request}}`. Ellen does the snapshot step of Packaging with that token.
- A live pass is never interrupted: a queued request waits for it (the busy case below).

**Nothing buildable is stranded** (D2, Terra S1: `end_pass` can make one request buildable
while another waits). `end_pass` answers `next: "build"` for its own request as today,
and `more: true` when a queued request waits; `record_delivery` and every package
continuation whose `next` is null answer `more: true` the same way. SKILL: whenever a
package flow finishes (the send recorded, or a continuation with `next` null), call
`continue_pass()` once more and do what it returns. `continue_pass` prefers a buildable
request whose lease lapsed over starting a queued round, as it does today.

So a round chains to the next inside Ellen's turns that the delegations' notifications
already start. A round whose Gmail round dies inside Ellen's turn (no delegation to
notify) waits for the next `continue_pass` — any accounting turn or the Monday cron —
as every pass's Gmail round does today (no regression; stated).

**Asking for a package** — `begin_pass(trigger="package", quarter, channel,
reply="telegram")` (quarter and channel move here from the snapshot step's start). In
Packaging this is Ellen's FIRST call, before `continue_pass` (D2, Astra S2: continuing
earlier work first could end her turn at a pending delegation before the ask was ever
recorded). If it answers `queued`, she sends its text, then does `continue_pass()` and any
earlier continuation as rule 1 says; the queued request follows that work.

- An open request for Q in `queued` or `snapshot` exists → nothing new; answer
  `{"status": "already", "text": "The <Q> package is already on its way — it follows when
  the check is done."}`.
- An open request for Q that is buildable (`snapshot-done`) or `built` and not staged is
  superseded by the new ask, as `_open_request` does today: the operator asked again, the
  new request is checked afresh and is the one that arrives (Terra D3, answered: not a lost
  package). A staged one is left to settle; the new ask queues or starts beside it.
- Otherwise the request is opened (superseding an unstaged open one for Q, as
  `_open_request` does today). No live pass → the pass starts bound to it (`snapshot`),
  answer as today plus `request`. A live pass (the `busy` case) → the request is
  `queued`, answer `{"status": "queued", "text": "A check is running — the <Q> package
  follows when it ends."}`; Ellen sends it and stops. The running pass's `end_pass`
  answers `next: "continue"`, which starts the round.
- `record_step(step="snapshot", action="start")` takes no quarter/channel now: they are
  the pass's request's.

**What the operator hears.** One line when the work starts ("Checking the bank and your
email for Q3 — the package follows when that's done.", or the queued line), then the zip.
Rounds after the first run with `reply="silent"`: Ellen sends only `speak`s (the store's
own notices, as today) — no progress lines.

**The Gmail round and judging, quarter-scoped.** The snapshot continuation of a package
pass carries `work = work.work_list(conn, quarter=Q, since=request.created_at)` — Q's
work items not yet searched in this request, first page — and `judge_due` restricted to Q;
`next = "gmail-round"` (or `end-pass` when stopped, not imported, or `can_run` false, as
for the sweep). Ellen runs step 4 of the pass on it (probe first; searches; `record_search`
for every item; the self-mail search), then starts the judge step (always, in a package
pass: judging is what a round is for) with `quarter` in its context; the specialist's
triage is `list_quarter_state(triage=true, quarter=Q)`. The judge step's `due_at_start`
and `_judgment_owed` are restricted to Q in a package pass.

**The check is bound to the import it ran on** (D2, Astra S1: an import landing between
the check and the build — a cron pass, say — added payments nobody searched for). When
`round_fate` makes a request buildable it stores `checked_snapshot := latest_import`.
`build_quarterly_package` and the request's first `stage_for_delivery` require the latest
import to be `checked_snapshot`; if a newer one landed, the request goes back to `queued`
(token, lease and `package_id` cleared, `round` and `remaining` kept, committed on its
own) and the call refuses: "the bank was re-read since the check — the check runs again;
call continue_pass". This replaces 0.3.5's "run step 1 again, then build again, once".
An import that revokes a request's staged first send (`revoke_superseded_first_sends`)
requeues that request the same way instead of closing it `revoked`: the operator asked
for the package, and it still follows.

**A package's first send needs its request** (D3, Astra S1: requeueing clears a request's
`package_id`, and `stage_for_delivery` skipped the token fence for a package no request
owns). A first send (not `resend`, not `last_built`) is refused unless the package's
owning request holds it (`package_id` = it, state `built` or `staged`) and the
`package_token` matches.

**Build and caption.** Unchanged except the caption adds, from the request's
`check_json`: "The email search couldn't run, so documents emailed since the last check
may be missing." or "<n> payments couldn't be searched or judged in full — say \"rebuild
it\" to try again."

**Sending the previous build.** `apply_reply` recognises "send (me) the last/previous
package (you built) (for Q3)" → instruction `send last <quarter>` (quarter optional).
Ellen calls `stage_for_delivery(channel, last_built=true, quarter=Q?)`: the most recently
built package (of Q when named) is staged token-free as the exact file, whatever was
imported since and whether or not it arrived; refused only when none was built or its
latest send is staged right now. The delivery is marked `as_built`; an import never
revokes an `as_built` send (the operator asked for that build). It returns the stored
caption with a first line "Built on <date>, as it was then." "Send it again" is unchanged.

### What does not change

The token/lease machinery, the stale-pass reclaim, delivery custody, revocation of
ordinary first sends, the weekly cron pass (still every open item), handovers, the
freshness rules of a build (`_require_current_snapshot`, the rebuild-once refusal).

### Residuals (stated)

- A round whose Ellen turn dies during its Gmail round waits for the next
  `continue_pass` (as every pass's Gmail round today).
- While a package's rounds run, a Monday cron finds the store busy and skips that week's
  check (as it does today for any running pass); the next Monday runs it.
- A round whose snapshot step cannot read the bank closes the request `recovery-failed`,
  as today; a later ask starts again.
