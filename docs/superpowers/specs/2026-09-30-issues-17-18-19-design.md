# Issues #17, #18, #19 — a package round fits Ellen's turns; a judgment says how far it got; a document's date is the one printed on it

Issues: bonzanni/casa-plugin-quarterly-accounting#17 (bug, severity:high), #18 (bug,
severity:low), #19 (bug, severity:low). Plugin 0.4.0 → 0.5.0 (record_match and
propose_match take a new required argument). Schema unchanged (6).

Status: converged 2026-09-30 — code round C2 on 3962324: Astra SHIP, Terra SHIP (all runs
`medium`). Design round D1 (e9bfb44): Astra DNS, Terra SWF — one shared S1 (an
async delegation ending without its step's finish strands the round) and one shared S2
(portal items starve the chunk), folded in below (marked D1); Terra's second S2 (the tool
schemas must carry `document_date`) is an implementation note, taken. Design round D2
(e8f8ae7): Astra DNS (two S1), Terra SWF (one S2) — all three are patches to the binding,
not a new mechanism, folded in below (marked D2). Code round C1 (b8c1723): Terra SHIP,
Astra DNS — two S1 that both need two delegation ids sharing their first 8 characters
(32 random bits of a uuid4): a prefix shared with an older pass's delegation now binds
nothing (the uniqueness check covers every delegation ever recorded); a shared prefix
leaves the step to its expiry, as in 0.4.0 (stated residual). Code self-review changed
the chunk loop's progress rule (below: "What a chunk handed out").

## Part A — issue #17: a package round never outgrows the turn that runs it

### What happens today (0.4.0)

A package round is: snapshot delegation → Ellen's Gmail round over the continuation's
`work` (up to `TRIAGE_LIMIT` = 50 items of the quarter) → `record_step(judge, start)` and
the judge delegation → `end_pass`. The delegations are `mode="sync"`: Casa waits up to
60 s and, if the specialist answers by then, the answer lands **inside the same Ellen
turn**, which carries on. Ellen's turn has 20 SDK turns (Casa's assistant role).

Live (issue #17): one Ellen turn held `continue_pass`, the snapshot delegation, ~48
`record_search`es, the judge start and a judge delegation that answered `ok` in time.
The turn ended on `max_turns_reached` (21 of 20) before `end_pass`. The store was
consistent and resumable — the judge step finished, unclaimed, so any `continue_pass`
would have continued it — but **nothing called `continue_pass`**: the judge's answer was
spent inside the dead turn, so no delegation notification was owed. The request waited
25 minutes, until the operator asked; without them it would have waited for the Monday
cron (up to 7 days) or a stale reclaim (3 h, and only if something begins a pass).

Casa has no other wake a plugin can use here (checked against ha-casa-app v0.332.16):
background jobs (`start_job`) load only the declaring plugin (no Gmail) and grant no
`delegate_to_agent`; plugin triggers are webhooks; `set_reminder` sends the operator a
message. The one wake is a **delegation's notification**: whatever way a delegation ends
(answer, failure, time-out, orphaned by a restart), Casa starts a turn for the resident
that made it — **if** the delegation did not answer inside that resident's turn.

### The property

> **Every Ellen turn of a package round does a bounded amount of work, and ends at a
> delegation whose notification starts the next one.**

Two things break it today, and the change fixes each:

1. A sync delegation can answer inside the turn, so the turn goes on (the next step, and
   the one after). → **Package-round delegations are `mode="async"`**: Casa returns
   `pending` at once and always notifies. Ellen ends her turn at every `pending`.
2. The Gmail round is as long as the quarter's work list (≤ 50 items; a first catch-up
   has more). → **The Gmail round is handed out in chunks of `GMAIL_CHUNK` (10) items**,
   and a chunk ends at the judge delegation. The round loops chunk → judge inside ONE
   pass (one bank sync per round, not per chunk) until the quarter's items are searched.

### The round, new shape

    snapshot (async delegation)                    ── Ellen's turn ends
    → [ Gmail chunk (≤ 10 items) → judge (async) ] ── Ellen's turn ends at each judge
        … repeated while items remain and the last chunk searched something
    → end_pass → round_fate (unchanged)

Ellen's turns in a round, each bounded:

- **Round start** (the ask, or the turn that ended the previous round / pass):
  `continue_pass` → `record_step(snapshot, start)` → `delegate_to_agent(async)` → end.
- **Snapshot continuation** (a notification): `continue_pass` → Gmail probe → the chunk
  (≤ 10 items, searched in parallel batches) → the self-mail search and the Telegram inbox
  sweep (first chunk only: its `step` is `snapshot`) → `record_step(judge, start)` →
  `delegate_to_agent(async)` → end.
- **Judge continuation** (a notification): `continue_pass` → either `next: "gmail-round"`
  (the next chunk: probe, chunk, judge, end — as above, without the self-mail search) or
  `next: "end-pass"` → `end_pass` → build and send, or `continue_pass` for the next round
  (rule 8), whose snapshot delegation ends the turn.

Measured budget: in the incident one turn carried ~48 items plus two delegations and
continuations in 21 SDK turns (parallel tool calls), i.e. about 3 items per SDK turn.
A chunk turn's fixed cost is about 6 SDK turns (claim, probe, record, start, delegate,
close); 10 items at a third of that rate still leave half the budget.

### Server changes

**The chunk.** `work.work_list(conn, req)` (a package round's continuation) hands out at
most `GMAIL_CHUNK` items of `package_work` — portals excluded **before** the chunk is cut
(D1, Astra S2 + Terra S2: ten portal items ahead in pid order filled the chunk, the round
searched nothing and shipped `unfinished` with a searchable item behind them), in pid
order. `total` and `remaining` count the whole unsearched list. The cron / operator pass
is unchanged (`TRIAGE_LIMIT`, portals listed and skipped by Ellen).

**A delegation's end ends its step** (D1, Astra S1 + Terra S1). With async delegations
every answer arrives as a notification, and today a notification's `continue_pass` finds
a step whose delegation failed early — or answered without the specialist finishing it —
still *running* until its 600 s expiry; that turn ends with nothing pending, and the
expiry wakes no one. The delegation's end is the evidence the step is over, so it closes
the step, bound by Casa's delegation id:

- `record_step(pass_token, step, action="delegated", delegation_id=<Casa's id>)` — right
  after `delegate_to_agent` answers with a `delegation_id`. Stored in the step's carry as
  `delegation` (an earlier one moves to `delegations_before`: a re-delegation). Refused
  unless the token is the live one and that step was started and is the running one —
  except that a step already **finished** answers `bound: false` (D2, Astra S1: a sync
  delegation that answered in the turn finished its step first; refusing the binding
  would have stopped an ordinary flow on the skill's refusal rule).
- `continue_pass(delegation_id=<the id the notification names>, delegation_status="ok"|
  "error")` — on every notification about a delegation to finance (a restart orphan is
  `error`). In a transaction of its own, committed **before** the claim reads its
  candidate (D2, Astra S1: closing the step inside the claim's transaction changed the
  candidate under the claim's re-check, and every retry rolled the closure back): if the
  live pass's latest step is unfinished and its recorded `delegation` equals the given id
  or starts with it (the given id at least 8 characters — Casa's notice prints the first
  8 of a uuid4), and no other delegation ever recorded (any pass's step's `delegation`
  or `delegations_before`) starts with it (D2, Terra S2; C1, Astra S1: a prefix shared
  with a replayed older delegation, in this pass or an earlier one, binds nothing), that step is finished as the resident: `failed` when
  the status is `error`, else a countless finish (the specialist came back without its
  own); a kept stop (issue #10) stays. Then the claim proceeds as always. An id that
  matches no running step (a replayed or stale notice, a step already finished, a
  restarted judge carrying a newer delegation) changes nothing.
- This applies to every flow's delegations (the rules are the skill's shared rules 2 and
  5), not only packages: it closes the same gap for a sync delegation that degraded to
  `pending` and then failed, which 0.4.0 also left to expiry.

**The judge step repeats inside a package pass.** `steps.start(step="judge")` in a
package pass whose judge step has already run is a **restart**: allowed only when that
judge step has *finished* (not running, not expired, not errored); it rewrites the same
`pass_steps` row (the primary key stays `(pass_id, step)`: no schema change):
`started_at := now`, `finished_at, finished_by, finish_json := NULL`, `carry_json := the
new carry` (its `report`, its fresh `due_at_start` for the quarter, and the sequence
marks below). The same transaction sets `pass_marker.claimed_step := NULL`, so the
restarted step, once finished, is claimable again (today a claim keys on the step's
*name*: a finished `judge` whose name equals `claimed_step` under a fresh lease would read
as "already claimed", and the round would wait out `LEASE_S`). Outside a package pass a
second judge start is refused as today.

The row always describes **the latest judgment**; `package_check` (`unjudged`, `whole`,
`incomplete`) reads it as today. Earlier judgments of the round leave nothing behind —
they only judged earlier chunks' documents, and the last judgment re-triages the whole
quarter.

**What a chunk handed out.** Every package continuation that hands out a chunk (the
snapshot's, and a judge's with `gmail-round`) records on the round's snapshot row
`handed := work.total` — the quarter's items still unsearched for the request at that
moment. (Code self-review: a first version counted "some item searched since the last
judgment", which a search of an item already searched satisfied without progress.)

**The judge continuation** (`steps._claim_pass`, step `judge`, a package round):

    next = "gmail-round"  iff  the judge step ended `finished` (not errored, not expired,
                               not stopped)
                          and  this pass's Gmail probe is ok
                          and  0 < len(package_work) < handed
    otherwise next = "end-pass"  (as today)

With `gmail-round` the continuation carries `work` (the next chunk, and a new `handed`)
and `judge_due`, like the snapshot continuation. The loop ends: the unsearched count is a
non-negative integer that must fall with every chunk; it can rise inside a pass only by
an operator's reply reviving an item, which is finite. A judge that errored or expired
ends it too (so a delegation that fails at launch — Casa busy — never makes Ellen loop
inside one turn). What the pass could not finish, `round_fate` handles exactly as today:
another round while `remaining` falls, else the package ships `unfinished`.

**Unchanged:** `round_fate`, the progress rule, the request states, the claim and
token machinery, `_judgment_owed` (not applied to package passes), the cron and
operator pass, handovers.

### Skill changes (Packaging, step 2; shared rules 2 and 5)

- Rule 2: after `delegate_to_agent` returns a `delegation_id`, `record_step(…,
  action="delegated", delegation_id=…)`. Rule 5: every notification about a delegation
  to finance → `continue_pass(delegation_id=<the id it names>, delegation_status=…)`.
- Both delegations of a package round are `mode="async"`; at `pending`, end the turn
  (round 1's turn has said its one line; later turns say nothing).
- The Gmail round works the continuation's `work` — at most 10 items — **in parallel
  batches** (one call per item per turn: all searches, then all downloads, then all
  filings, then all `record_search`es), then always starts the judge step and delegates
  it (async). The self-mail search and inbox sweep belong to the snapshot continuation's
  chunk only.
- A judge continuation's `next` is `gmail-round` (another chunk, same token rules) or
  `end-pass`.

### Residuals (stated)

- A chunk turn that still dies (a chunk costing more than its budget, a Casa restart
  mid-turn) waits for the next `continue_pass` — the same gap as today, now needing a
  chunk of 10 items rather than a whole quarter to open it. Casa's half (a turn that ends
  on its limit tells the operator) is ha-casa-app#1121. Likewise a turn that dies between
  `delegate_to_agent` and `record_step(delegated)`: the notification cannot be bound to
  the step; a step the specialist finished continues as always, one it did not waits
  for its expiry. The same holds when two recorded delegation ids share their first 8
  characters (Casa's notice shows no more): the notice binds nothing — never the wrong
  step — at a chance of about one in four billion per pair of uuid4 ids.
- The weekly cron pass and "go and check now" keep one Gmail round of up to 50 items in
  one turn and sync delegations: the same exposure, not in this issue's scope (a
  follow-up issue is proposed, not filed).
- Each chunk costs a judge delegation that re-triages the quarter: more specialist time
  per round, bounded by the judge's 510 s wrap-up; no extra bank sync.

## Part B — issue #18: a judge finish says how far triage got

### What happens today

`t_step` parses `triage_remaining` but nothing requires it. A specialist's judge finish
`{remaining_in_cycle: 0}` is stored; `package_check` counts a judgment whole only when
`triage_remaining == 0`, so the round counted `incomplete` and ran again although the
judge had covered everything. Separately, Ellen twice ended a package round without
starting the judge step; each cost a full round.

### The change

1. **A judge finish that carries any count must carry `triage_remaining`.**
   `steps.finish(step="judge")`: when the finish is not `failed`, not `stopped` and
   carries at least one count, `triage_remaining` is required; otherwise refused, naming
   the field: "a judge step's finish carries triage_remaining — the last triage page's
   `remaining` (0 when every page was judged); finish again with it". A countless finish
   (Ellen's, when the delegation came back without one: `finished_by = resident`) is
   still accepted, and still counts as not whole — it cannot say how far triage got.
   The refusal comes before the "already finished" answer only for a step that is still
   open; an already-finished step answers `already` as today.
2. **A package round is not ended without a judgment.** `end_pass` of a pass holding a
   package request in `snapshot`, with outcome `complete` or `interrupted`, that imported
   the bank (a `snapshots` row of its own), whose snapshot step was not stopped, and that
   has no judge step: refused — "not ended: this package round has not judged its
   quarter. Start the judge step (record_step step=\"judge\"), delegate it, and end the
   pass after it". `stopped` and `failed` are never refused (nothing to judge after a
   stop or a failed read).

## Part C — issue #19: the date that names a file is the date printed on it

### What happens today

Ellen files a Gmail attachment with `document_date=<her provisional reading>` (often the
email's date). The specialist reads the PDF before matching and is told to correct the
reading with `update_document_metadata`, but nothing asks for the date; four documents
of a live quarter shipped named with the email's date (`package.doc_filename`:
`<document_date>_<issuer>_<amount>`).

### The change

`record_match(author="auto", …)` and `propose_match(…)` take a required
`document_date`: **the date printed on the document (its issue date — not a due, delivery
or email date), read from the file just opened**. In the match's transaction, before
the pairing is appended: validated (`YYYY-MM-DD`); if it differs from the stored
`document_date`, the document is updated and `lineage.settle_doc_holders` runs, exactly
as `update_document_metadata` does. A machine pairing can no longer be written without
the specialist stating the date it read. The operator's paths (`record_match(author=
"operator")`, `confirm_match`, `apply_reply`) are unchanged: a proposal the operator
confirms was written by `propose_match`, which carried the date.

The skill's auto-match bar (step 6) says the same: read the date on the document; the
window is measured from it; pass it as `document_date`.

### Residuals (stated)

- Documents paired before 0.5.0 keep whatever date they were filed with (the four of the
  issue's quarter included) until a later machine write about them — a rematch or
  proposal — restates it. The operator's own pairing of a document the specialist never
  judged keeps the filed date.
- The value is the specialist's reading; the server cannot check it against the file.

## Testing

- Part A: a package round of 25 unsearched items runs chunk → judge → chunk → judge →
  chunk → judge → `end-pass` in one pass (one import), each chunk ≤ 10; the claim after
  each restarted judge is immediate (no `LEASE_S` wait); a chunk that searches nothing
  ends the pass; an errored or expired judge ends the pass; a judge restart while the
  judge runs, or outside a package pass, is refused; `package_check` reads the latest
  judgment only; the cron pass still hands out up to 50 items and refuses a second judge;
  ten portals ahead of a searchable item do not hide it. A delegation notice bound to the
  running step (error, or ok without a finish) closes it and the same `continue_pass`
  continues it; an unbound, stale or short id changes nothing; a notice for judge 1
  after the judge was restarted leaves judge 2 running.
- Part B: a judge finish with `remaining_in_cycle` and no `triage_remaining` is refused
  and the step stays open; a countless or `failed` finish is accepted; `end_pass`
  refuses a package round with no judge step after an import, accepts it `stopped` /
  `failed` / without an import.
- Part C: `record_match(auto)` / `propose_match` without `document_date` are refused; a
  differing date is stored on the document and the package names the file by it.
- Mutation-check each new guard (in a worktree).
