## #48 — one purchase backs at most one payment

### The defect
A vendor email carrying an invoice AND a receipt for one purchase is filed as two documents
with the same issuer and number (ElevenLabs May: doc 24 `Invoice-CUWVSRB8-0002` + doc 25, a
receipt read as `CUWVSRB8-0002`). May was proposed with doc 24 (alternatives [25]); an
alternative holds nothing (rev 18.4 §R18.4), so doc 25 was free, and July's payment was then
PROPOSED with doc 25 without a search. Same again August → September (docs 73/74).

### Measured (replay of the rule against the stores' decisions) — settled
- Q2 re-run #3 (103 decided, 73 held docs): refuses exactly rows 1973 (doc 25) and 1931
  (doc 74), both the WRONG proposals. Q2 run 1 (28 decided): refuses nothing.
- SnelStart key: the one invoice linked to two payments (OpenRouter EITIZBQ1-0005) is a key
  error, already adjudicated (-0006). No instalment / part-payment / refund-vs-invoice case.

### The rule
**A purchase** = every document with the same issuer and the same document number, compared
as `documents.collisions` already compares them (lower/trim of `document_number` and of
`coalesce(issuer, counterparty)`). A document with no number (or no issuer) is a purchase of
its own. Membership ignores `irrelevant` and `sha256` (ownership is about what is held).

**A purchase is held** when any of its documents is held (`matches.holders`, unchanged: a
match, a proposal's primary, a joint set). **`matches.taken_elsewhere(doc, pid)` becomes
purchase-wide**: held by another payment through ANY document of the purchase.

Its readers — all the job's side, so all move together:
1. the floor `matches._floor_doc` (chosen document and each alternative) — the refusal;
2. `loop._fits_exactly` (the reopening's exact fit);
3. the candidate list in `loop.candidates` (skip a document whose purchase is MATCHED
   elsewhere; `held: "other"` when its purchase is held elsewhere) — job_next shows the twin
   as taken before the model tries it;
4. `cards._offered` (an alternative whose purchase another payment holds is not offered);
5. `replace.ask_in_tx` — the job's `replace` answer to a handover (d1 Astra S1): a document
   whose purchase another payment holds is refused there too;
6. `replace.open_ones` — a stored replace question (the job's offer) whose new document's
   purchase is now held by another payment is retired (superseded) like one whose payment
   left scope, so its card is never rendered (d2 Astra S1).

The complete list of the job's ownership sites (d2: checked by enumeration, not by finding
one more): the floor (1), the exact fit (2), the candidates and the re-walk that reads their
`held` (3), the card's offered alternatives (4), the replace question at its creation (5) and
while it is open (6), and the job's metadata edit (below). The operator's answer to the
   replace card (`replace.answer_in_tx`, `_require_unheld`) stays per document.

**Unchanged:** `holders` (per document) and every operator path that reads it
(`_require_unheld` in confirm / pick, `replace.py`), `settle_doc_holders`. The operator's tap
is not limited by the purchase rule: the floor is the job's.

**The refusal names the payment it already backs**, e.g. `document #25 is the same purchase
as document #24 (Eleven Labs Inc. CUWVSRB8-0002), which already backs the payment of
2026-05-01 (EUR 18.94): one purchase backs one payment — search for this payment's own
document`.

**The job's metadata edit (d1 Terra S1).** `update_document_metadata` WITH the pass token
(the job's reading) is refused when its issuer / counterparty / document_number change
would make one purchase held by two different payments (resolved pids); the refusal names
the payment, as at the decide. Precedent: `mark_irrelevant` refuses on a matched document.
Without the token (the operator's words) the edit is applied: the operator is not limited.
`ingest_document` of the same bytes never rewrites issuer or number, so this is the one
edit site.

### Not done
No date window. No new state (the purchase is computed from `documents` at the read).

## #50 — `missing` is refused while a vendor email naming the payment is unlisted

### The defect
Megekko 1 (row 2031) was decided `missing` on its first pass although its own order-number
search (`ME280426000457`) returned "Bestelling is verzonden" (19dd52ffe4f84727), which
carries M003188553.pdf. The model listed attachments only on another email. It recovered only
by a same-run re-walk after Megekko 2 taught the hint.

### What the server can see — the honest limit
`search_emails` / `list_attachments` are Casa's Gmail tools; the plugin server sees neither.
Its one carrier is `record_search`, model-reported. So this floor is **a reminder the model
fills in: it catches a skipped step on an honest report, not an omitted email or a
mislabelled query.**

### Measured (the narrow reading against run #3's transcripts) — settled
31 applied `missing` decisions. Reading "every vendor email returned" would refuse 31/31
(441 listings owed). The NARROW reading (emails returned by a search on the payment's OWN
reference / order number) refuses 2/31: Megekko 1 (the fix) and Amazon row 2044 (6 listings,
outcome unchanged: portal invoice, decided `missing` again).

### The rule
- `record_search` gains `emails`: `[{"id": <message id>, "listed": true|false}, …]` — the
  vendor emails a search on the payment's OWN reference or order number returned, each with
  whether its attachments were listed (what a listing found goes in `refs`, as today). A
  plain vendor or date search reports none (`emails` omitted or `[]`).
- An email reported `listed: false` is an item the payment owes: `run_items` kind `email`,
  unit `payment:<pid>`, key the message id (the existing per-run queue — the store already
  holds it; schema 14 → 15 only widens the `kind` CHECK, a table rebuild).
- It closes when a later `record_search` for the payment reports it `listed: true`, or
  reports a ref of that message (`<id>:<att>`, a listing implied).
- **`decide` outcome `missing` is refused while the payment has an `email` item not `done`
  (queued, or given up with a payment a handover later reopened — d1 Astra S1); the
  refusal names the email(s)** and says how to report the listing. `match` / `propose` are
  not blocked by it (it is a check on `missing` alone).
- A listing report (`record_search` with no `queries`, `emails` given) is **not a search**:
  it does not count toward SEARCHES_MAX nor add to `searches`; otherwise a payment that used
  its 3 searches could neither report the listing nor decide `missing`.
- `job_next` hands the payment's unlisted (not `done`) emails with it (`emails_to_list`), so a cut
  between the report and the decide does not lose them.
- An `email` item is never stamped as a hand-out's `files`, so it is given up only with its
  payment (queues.settle's existing "the payment is given up: so is what it owes").
  `queues.gave_up_upstream` reads only the UPSTREAM kinds (erase, search, ref) — a given-up
  email item does not turn every other `missing` into "search incomplete" (and its own
  payment cannot be decided `missing` while it is not done, so it reads "search
  incomplete" by the existing outcome-NULL line). Likewise `queues.given_up` (the end's
  per-kind lines and the run's `partial` flag, loop.py ~672) reads only the UPSTREAM kinds:
  an email item is never a give-up of its own (d2 Astra S2).
- A listing report closes the payment's email item whether it is `queued` or `given_up`
  (d2 Terra S2: a handover-reopened payment must be able to clear it).
- Before the run's work list exists (no job), `emails` is ignored, as `refs` is.
- The skill (quarterly-job step 3) says: on a search by the payment's own reference or order
  number, report every vendor email it returned in `emails`, listed or not.

### Not done
No Casa change; no server-side Gmail; no check that the query really is the reference (it is
model-reported free text). No date window.

### Precedence — first claim wins within a run (operator ruling A, 2026-10-07; d1 Astra S1)
A purchase belongs to the first payment whose decision takes it. If a LATER payment wrongly
takes an earlier `missing` payment's purchase (July 5 decided missing; July 6's search files
July 5's invoice and receipt and proposes the receipt), the earlier payment is not re-walked
in that run (its candidates are held elsewhere) and stays `missing` until the next check.
The operator rejects the wrong proposal, as with 0.11.0; the next check finds the purchase
free. Accepted cost, documented in the CHANGELOG; no precedence machinery.
